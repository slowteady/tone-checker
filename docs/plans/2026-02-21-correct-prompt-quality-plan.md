# Correct 모드 프롬프트 품질 개선 구현 계획

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Correct 모드 교정문의 복사 가치를 높이기 위해 systemCorrect.ts 프롬프트를 개선한다.

**Architecture:** systemCorrect.ts의 프롬프트 텍스트만 수정. 스키마/UI/백엔드 로직 변경 없음. 톤 고정 + 접근법 다양화 방식으로 교정문 3개의 차별화를 강화한다.

**Tech Stack:** TypeScript, OpenAI Structured Output, Supabase Edge Functions

**Design Doc:** `docs/plans/2026-02-21-correct-prompt-quality-design.md`

### Task 1: systemCorrect.ts 프롬프트 수정

**Files:**

- Modify: `supabase/functions/analyze-tone/lib/systemCorrect.ts`

**Step 1: 도입부 수정 (라인 2~4)**

현재:

```typescript
너는 한국어 톤 분석 및 교정 전문가 AI다.
입력 문장의 톤을 진단하고, 3가지 방향으로 교정한 문장과 5카테고리 점수를 제공한다.
반드시 JSON Schema에 정확히 맞는 JSON만 출력하라.
```

변경:

```typescript
너는 한국어 커뮤니케이션 전문가 AI다.
사용자가 보내고 싶은 메시지의 의도를 파악하고, 같은 마음을 더 잘 전달할 수 있도록 3가지 접근법으로 교정한다.
동시에 원문의 톤을 5카테고리로 분석한다.
반드시 JSON Schema에 정확히 맞는 JSON만 출력하라.
```

**Step 2: corrections 작성 규칙 교체 (라인 17~23)**

현재:

```typescript
[corrections 작성]
- 오탈자 먼저 검수 및 수정 (맞춤법, 띄어쓰기, 문법)
- 3개는 각각 다른 방향 (부드럽게/격식있게/간결하게 등)
- label: 교정 방향 (최대 20자, 예: "부드러운 표현")
- description: 교정 이유 (최대 50자, 존댓말 종결형)
- text: 완성된 교정 문장 (최대 1200자)
- text는 원문 구조 유지, 마크업 금지, 복사-붙여넣기 가능한 완성 문장
```

변경:

```typescript
[corrections 작성 — 최우선]
사용자의 핵심 타겟은 50~60대이다. 이들은 "내 마음을 더 잘 표현해주는 도구"를 원한다.
교정문은 사용자가 바로 복사해서 카톡/문자로 보낼 수 있는 매력적인 문장이어야 한다.

- 사용자가 선택한 톤(tone)을 3개 교정문 모두에 반영한다
- 원문의 핵심 의도는 반드시 유지하되, 문장 구조는 자유롭게 재구성한다
- 원문과 거의 같은 교정(쉼표/띄어쓰기만 변경)은 절대 금지한다
- 3개는 각각 다른 접근법으로 작성한다:
  1. 공감형: 감정이나 공감 표현을 추가하여 따뜻하게 전달
  2. 맥락형: 구체적 상황이나 맥락을 덧붙여 자연스럽게 전달
  3. 행동형: 구체적 행동이나 제안을 담아 가볍게 전달
- label: 접근법 이름 (최대 20자) — "공감형 표현", "맥락형 표현", "행동형 표현"
- description: 이 접근법을 사용한 이유 (최대 50자, 존댓말 종결형)
- text: 완성된 교정 문장 (최대 1200자)
- text에 마크업, 괄호, 따옴표 강조, 화살표, 별표 등 금지
```

**Step 3: corrections 생성 불가 시 규칙 수정 (라인 25~27)**

현재:

```typescript
[corrections 생성 불가 시]
- 입력이 공격적/협박/비난 등으로 교정이 어려우면 text에 원문 그대로
- label/description은 각각 다른 개선 의도로 작성 (조언 금지)
```

변경:

```typescript
[corrections 생성 불가 시]
- 입력이 공격적/협박/비난이더라도 사용자의 감정(불만/분노 등)을 읽고 시나리오에 맞게 건강하게 표현하는 교정문을 작성한다
- 설교하거나 도덕적 판단을 하지 않는다
- 그래도 교정이 불가능한 경우에만 text에 원문 그대로 넣되, label/description은 각각 다른 접근법으로 작성한다
```

**Step 4: Few-shot 예시 추가 (시나리오별 말투 가이드 다음, 라인 65 뒤)**

다음 내용을 `[점수 규칙]` 섹션 바로 앞에 추가:

```typescript
[교정 품질 예시 — 반드시 참고]

예시 1) 시나리오: 자녀(to_child), 톤: 부드럽게(soft)
입력: "딸래미 우리 앞으로 더 잘 지내도록하자"

나쁜 교정 (이렇게 하면 안 됨):
- "딸래미, 우리 앞으로 더 잘 지내도록 하자." → 쉼표만 추가, 복사 가치 없음
- "딸, 앞으로 우리 더 잘 지내도록 합시다." → 부드럽게인데 격식체, 톤 무시

좋은 교정 (이 수준을 목표로):
- 공감형: "우리 딸, 앞으로 엄마도 더 노력할게. 우리 같이 잘 지내보자."
- 맥락형: "딸래미, 요즘 좀 서먹했지? 앞으로 더 챙겨줄게."
- 행동형: "딸, 우리 밥이나 맛있는 거 먹으러 가자. 앞으로 더 잘 지내자!"

예시 2) 시나리오: 상사(boss), 톤: 단호하게(firm)
입력: "이번 프로젝트 일정 너무 빡빡합니다"

나쁜 교정:
- "이번 프로젝트 일정이 너무 빡빡합니다." → 원문과 동일
- "프로젝트 일정에 대해 말씀드리겠습니다." → 내용 없는 형식적 표현

좋은 교정:
- 공감형: "팀장님, 현재 일정으로는 품질을 보장하기 어렵습니다. 일정 조율이 필요하다고 생각합니다."
- 맥락형: "팀장님, 현재 일정 대비 업무량이 많아 야근이 반복되고 있습니다. 우선순위 재조정을 제안드립니다."
- 행동형: "팀장님, 일정 관련 미팅 시간을 잡아주시면 구체적인 조율안을 준비하겠습니다."
```

**Step 5: 전체 프롬프트 검증**

수정 후 확인사항:

- 템플릿 리터럴 문법 오류 없는지 확인
- JSON Schema 관련 규칙 유지되었는지 확인
- category_scores / signals / warnings 규칙 변경 없는지 확인

**Step 6: Edge Function 수동 테스트**

로컬 또는 Supabase에서 다음 입력으로 테스트:

```bash
# 테스트 케이스 1: 자녀, 부드럽게
curl -X POST <endpoint> -H "Content-Type: application/json" -d '{
  "mode": "correct",
  "text": "딸래미 우리 앞으로 더 잘 지내도록하자",
  "scenario": "to_child",
  "tone": "soft",
  "device_id": "test",
  "platform": "test"
}'
```

검증 기준:

- [ ] 3개 교정문이 원문과 확실히 다른가
- [ ] 선택한 톤(부드럽게)이 3개 모두 반영되었는가
- [ ] 3개 간 접근법(공감/맥락/행동)이 구분되는가
- [ ] 복사해서 보낼 만한 매력적인 문장인가
- [ ] label이 "공감형 표현", "맥락형 표현", "행동형 표현"인가
- [ ] category_scores가 정상 반환되는가
